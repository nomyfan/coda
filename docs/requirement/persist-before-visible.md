# 先存档，再对外说「做完了」

## Problem

系统把内容存进数据库，比它在界面上显示出来要晚一点。两件事各做各的，没有先后保证。

后果是：**用户在界面上看到的内容，数据库里可能还没有。** 任何从数据库读取的功能都会踩到这一点——它读到的是一个比用户眼睛看到的更旧的状态，而且无从知道自己读早了。

fork 是第一个受害者。它复制的是数据库里的内容，所以可能复制出一份少了最后一小段的副本，而且不报错（见 [`fork-session.md`](fork-session.md) 的 Known Limitations 第一条）。fork 目前用重试和校验兜了一部分，但 sub-agent 那部分兜不住，只能作为已知缺口接受。以后做导出、全文搜索、多实例部署，都会重新撞上同一堵墙。

**排查线索**（后续实现的起点，不是方案）：

- 主 agent：`driver.rs` 里先 `emit_event(LLMEnd)`，返回 `Done` 之后才在外层 `save_checkpoint`。
- sub-agent：更早一步——它先把 `Reply` 投递给调用方，之后才存自己的记录（`driver.rs` 的两处 reply 发送点）。
- hub：从事件流折出内存快照并把 `turn_running` 置否，走的是事件通道，不等数据库。

## Scenarios

- 用户看到 AI 回复完，立刻点 fork。数据库里还没有这条回复，fork 报错——用户不理解为什么刚看到的东西"不存在"。
- 主 agent 那一轮已经存好、某个 sub-agent 的记录还在路上，此时 fork 成功了，但复制出的会话里那个 sub-agent 少了一段记忆，**没有任何提示**。
- 数据库卡顿时，第 3 轮 sub-agent 的记录拖到第 5 轮都没存完。此时从第 3 轮 fork，同样会缺东西——这说明问题不限于最新一轮。

## Scope

**In**

- 调整存档与对外信号的先后：一轮对外表现为「结束」之前，它的内容（含 sub-agent 那部分）已经存好。
- 主 agent 和 sub-agent 两条路径都要覆盖。
- **确定崩溃时的取舍**（见 Constraints，这是本需求最核心的决策）。

**Out**

- 不改数据库结构。
- 不改 fork、rewind 的对外行为。它们自动受益：fork 现有的重试与校验补偿届时可以拆掉。
- 不追求分布式意义上的严格一致，只要求「数据库不落后于用户看到的」。

## Constraints

**投递语义会被反转，必须先想清楚要哪一种。** 今天的顺序是「先投递 Reply、后存档」，等于**至少一次**：崩溃在两者之间，恢复时投递目标还在旧记录里，Reply 会重发。

如果简单改成「先存档、后投递」，并在存档时把投递目标一并清掉，就变成**至多一次**：崩溃在存档之后、投递之前，恢复后调用方会永久等一个不会来的回复——这是死锁，比重发严重得多。

要既先存档又不丢投递，得存两次：先存（保留投递目标）→ 投递 → 再存（清掉目标），并要求调用方对重复的 Reply 幂等。这是三条路里唯一两头都占的，代价是多一次写和一个幂等要求。

其余约束：

- 不能让每轮的结束感知明显变慢。存档本来就在关键路径上，调换顺序不应额外增加等待。
- 崩溃恢复的行为要有测试覆盖，不能靠推理。

## Success Criteria

- 界面上一轮显示为结束时，该轮的全部内容（含 sub-agent 线程）已经在数据库里。
- 崩溃在任意时刻，恢复后要么调用方收到回复、要么它能重新收到，不出现永久等待。
- 重复投递的 Reply 被正确处理，不产生重复的工具结果。
- fork 去掉重试与落库校验之后仍然正确——这是本需求生效的验收标志。
- 每轮结束的感知延迟没有明显变化。
