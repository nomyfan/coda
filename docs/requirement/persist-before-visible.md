# 先存档，再对外说「做完了」

## Problem

系统把内容存进数据库，比它在界面上显示出来要晚一点。两件事各做各的，没有先后保证。

后果是：**界面上一轮已经显示结束了，数据库里可能还没存完。** 任何从数据库读取的功能都会踩到这一点——它读到的是一个比用户眼睛看到的更旧的状态，而且无从知道自己读早了。

fork 是第一个受害者。它复制的是数据库里的内容，所以可能复制出一份少了最后一小段的副本，而且不报错（见 [`fork-session.md`](fork-session.md) 的 Known Limitations 第一条）。fork 目前用重试和校验兜了一部分，但 sub-agent 那部分兜不住，只能作为已知缺口接受。以后做导出、全文搜索、多实例部署，都会重新撞上同一堵墙。

**排查线索**（后续实现的起点，不是方案）：

- 主 agent：`driver.rs` 里先 `emit_event(LLMEnd)`，返回 `Done` 之后才在外层 `save_checkpoint`。界面正是靠这条 LLMEnd 判断一轮结束的（`hub.rs` 的 `event_settles_turn`）。
- sub-agent：更早一步——它先把 `Reply` 投递给调用方，之后才存自己的记录（`driver.rs` 的两处 reply 发送点）。调用方收到 Reply 就继续往下跑，跑完剩下的半轮都可能比它存完更快。
- hub：从事件流折出内存快照并把 `turn_running` 置否，走的是事件通道，不等数据库。

## Scenarios

- 用户看到 AI 回复完，立刻点 fork。数据库里还没有这条回复，fork 报错——用户不理解为什么刚看到的东西"不存在"。
- 主 agent 那一轮已经存好、某个 sub-agent 的记录还在路上，此时 fork 成功了，但复制出的会话里那个 sub-agent 少了一段记忆，**没有任何提示**。
- 数据库卡顿时，第 3 轮 sub-agent 的记录拖到第 5 轮都没存完。此时从第 3 轮 fork，同样会缺东西——这说明问题不限于最新一轮。

## Scope

**In**

- 一轮对外表现为「结束」之前，它的内容（含 sub-agent 那部分）已经存好。「结束」指最终回复、中止、出错这三种收尾。
- 主 agent 和 sub-agent 两条路径都要覆盖。

**Out**

- 不改数据库结构。
- 不改 fork、rewind 的对外行为。它们自动受益：fork 现有的重试与落库校验届时可以拆掉。
- 一轮跑到一半时不作保证。审批挂起、某个工具刚跑完，这些时刻数据库落后多少都不管——fork 和 rewind 本来就只在会话空闲时才允许。
- 不追求分布式意义上的严格一致，只要求「数据库不落后于用户看到的那个结束」。

## Constraints

**顺序调过来之后崩溃会丢什么，已经定了。**

今天是「先投递、后存档」：sub-agent 把结果交给调用方之后才存自己的记录，中间隔着一整个数据库往返，卡顿时几百毫秒到几秒——这正是问题的来源。

调成「先存档、后投递」之后，风险窗口挪到「存完了、还没交出去」这一小段。这段是纯内存操作，微秒级。崩在这里，调用方收不到这个结果，那一轮就废了。

**这个代价可以接受，三条理由：**

1. 窗口比现在小几个数量级。顺序翻了个面，撞上的概率反而大幅下降。
2. 不会卡死。调用方停在「等回复」时，用户发下一条消息就会把它清掉：待回复的工具调用被记成「已中断」，然后重新开始。这条逃生口现在就有（`driver.rs` 里 `ToolExecution` 收到 `Task` 的分支）。
3. 想做到「崩溃后自动把这个结果补上」，光把它存下来不够。硬崩溃时 runtime snapshot 根本没写，恢复后没人会去驱动那个线程，存下来的东西没人读。要真兑现，得另加一套「开会话时扫描并补投」的机制——买到的东西配不上这个成本。

**中止这条路要单独想。** 用户点中止时，主 agent 不等 sub-agent 回话：它自己把所有待回复记成「已中断」就宣布这轮结束了，而 sub-agent 们还在各自收尾、各自存档。「先存后投」在这里管不住，因为压根没有投递这个动作。中止之后所有线程都回到空闲、fork 会放行，所以这条路必须有说法。

**其余约束：**

- 存不进去的时候，这一轮不宣布结束，明确报错，让用户知道没存上。现在是只打一行日志就当没事发生。
- 不能让每轮的结束感知明显变慢。存档本来就在关键路径上，调换顺序不应额外增加等待。
- 崩溃恢复的行为要有测试覆盖，不能靠推理。

## Success Criteria

- 界面上一轮显示为结束时，该轮的全部内容（含 sub-agent 线程）已经在数据库里。
- 数据库写不进去时，这一轮不显示为结束，用户看到明确的错误。
- 崩在「存完了、还没交出去」那一小段之后，会话不卡死：用户发下一条消息，残留的待回复被记成已中断，会话正常往下走。
- fork 去掉重试与落库校验之后仍然正确——这是本需求生效的验收标志。
- 每轮结束的感知延迟没有明显变化。
