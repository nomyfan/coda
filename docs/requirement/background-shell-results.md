## Problem

后台 shell 任务目前不能像 subagent 一样在 Background tasks 面板展开查看结果。
任务通知里的文本适合模型阅读，但前端不能依赖解析这段文本来获得输出、状态或任务关联。
本次结构化的目的，是支持任务结果展示，而不是单独改造报错。

## Scenarios

- 用户在面板展开已结束的 shell 任务，分别查看 stdout、stderr 和结束状态。
- 用户从 task notice 找到对应任务并查看输出；一条 notice 包含多个任务时，每个任务都有独立入口。
- 模型已经通过 task_output 读过输出，用户仍能查看 ring 保留的内容。
- 输出发生覆盖或被配额淘汰时，界面明确说明保留范围或不可用原因。

## Scope

- 提供结构化的 shell 结果数据：任务关联、结束状态、stdout、stderr 和输出覆盖情况；区分结果可用、过期、任务不存在及读取失败。
- 面板沿用现有结果展开交互，按任务类型展示 shell 输出或 subagent 答案。
- notice 使用结构化任务关联提供查看入口，前端不解析模型可读的 content 字符串。
- notice 仅保留任务信息、结束状态和读取提示，不保存输出；ring 淘汰后不能从历史通知恢复输出。
- 不改动 task_output 的增量读取语义，不增加模型重读能力；本次不要求运行中日志实时推送。

## Constraints

- 面板读取不推进 task_output 游标，不确认模型已收到结果，不影响完成通知投递。
- 读取范围受 ring 当前保留窗口限制，不承诺完整历史日志；沿用 session 配额淘汰机制。
- stderr 非空不等于任务失败，结束状态以退出码和运行时状态为准。
- 给模型阅读的文本与前端展示数据可以并存，不能把文本解析作为前端协议。

## Success Criteria

- 已结束的 shell 任务可以在面板展开查看，stdout、stderr 和状态各自展示。
- 单任务及多任务 notice 都能按任务定位结果；任务已不在面板近期列表时也能明确处理查看请求。
- 面板查看前后，模型的增量读取结果和通知确认状态不变。
- 覆盖、配额淘汰和读取失败有明确展示，不伪装成空输出或成功。
