# Fork Session

## Problem

现在想换个方向重试，只有 rewind 一条路，而 rewind 是破坏性的：回到某条消息重跑，原来那条路线就没了。

用户真正想要的是「保住已有结果，同时从中间某个点另开一条支线」。今天只能手动把上下文粘贴到新会话里重建，既麻烦，也没法还原 sub-agent 已经跑出来的成果。

fork 把这件事变成一次操作：选中自己发过的某条消息，复制出一份新会话，原会话原封不动。新会话带着**这条消息之前**的完整历史，而这条消息本身回到输入框里等着改——也就是一次**非破坏性的 rewind**。

## Scenarios

- 会话跑到第 5 轮，用户觉得第 4 轮那句问得不对，想换个问法重来，但第 4、5 轮的讨论还想留着——在第 4 轮自己发的那条消息上 fork，新会话只带前 3 轮，第 4 轮那句原样出现在输入框里，改一改再发。
- 一个会话攒了很长的上下文，其中有 sub-agent 跑出来的结果。用户想试一个有风险的方向，又不想污染它——从会话列表复制一份完整副本，在副本里折腾。
- 用户中断了一轮（不管是生成到一半还是工具跑到一半），想换个方向重来——在这一轮自己发的那条消息上 fork，中断的那一轮不进副本。

## Scope

**In**

- 在用户自己发的消息上 fork。新会话保留**这条消息所在那一轮之前**的全部内容，这条消息本身不进副本，而是填进新会话的输入框。
- 保留的内容包含 sub-agent 那部分，新会话可以直接接着跑。
- 从会话列表复制整份副本：不选分叉点，把源会话已保存的内容全部带走。这也是「从最新一轮之后接着分叉」的入口——正文里最后一轮之后没有下一条用户消息可挂。
- 新会话沿用源会话选的模型和名字。

**Out**

- fork 后不自动发消息。fork 完把用户切到新会话，发什么由用户决定。
- 不记录「从哪来」的溯源关系。两个会话 fork 完即完全独立，不加字段、不加 UI。
- 分叉的粒度是「一轮」，不是「一条消息」：分叉点只是用来指认「从哪一轮开始不要」。AI 的回复、中途调用工具的消息、工具结果上都不出现入口。
- 不能在 sub-agent 的消息上选分叉点。
- 会话第一条用户消息上不出现入口——它前面没有任何一轮，分出来会是个空会话。

## Constraints

- **源会话必须处于空闲状态**：正在跑或有待批准的工具调用时，拒绝 fork。与 rewind 的行为一致。
- 复制要么全部成功、要么全部不发生。失败时源会话完全不受影响。
- fork 不打断源会话——它不重启、不中断，正在看着它的客户端毫无感觉。

## Known Limitations

**一、fork 不保证是精确副本。** 极少数情况下，新会话里某个 sub-agent 会少最后一小段记忆，**而且不会有任何提示**。

原因是系统把内容存进数据库这件事，可能比界面上显示出来晚一点点。正常情况下，从用户看到回复到点下按钮的这段时间早就够存完了；只有数据库卡顿时才可能撞上。

**受影响的通常是最新一轮，但这不是保证。** sub-agent 存自己的记录不会拦住主线继续往下跑，所以数据库严重卡顿时，第 3 轮的 sub-agent 记录完全可能拖到第 5 轮都还没存完——那时从第 3 轮 fork 一样会缺它的末段。准确的说法是：**任何还有内容没存完的轮次都可能受影响**，只是越早的轮次越不可能。

根治要改动系统保存内容的时机，那是一件独立的后续工作，已单独立项：[`persist-before-visible.md`](persist-before-visible.md)。分叉点本身和主线内容能挡住（挡不住时会明确报错，重试即可），sub-agent 那部分挡不住——因此接受，并在此写明。

**二、待办清单带的是最新状态，不是分叉点当时的状态。** 从第 3 轮 fork，新会话里的待办清单是源会话**现在**的样子，而不是第 3 轮结束时的样子——第 4、5 轮改过的条目会跟着过去，agent 后续也读得到。

这是因为待办清单只存当前值、不按轮次留档，要做到"回到当时"就得改存储结构，超出本需求范围。行为与 rewind 现在的表现一致（rewind 同样不还原待办清单）。

## Success Criteria

- 在某条用户消息上 fork，得到一个新会话：内容止于它前面那一轮，这条消息出现在输入框里，源会话一字未动。
- 新会话可以立刻发消息并正常跑完一轮；保留下来的 sub-agent 记得自己之前做过什么——以上述 Known Limitations 为界。
- 从会话列表复制的副本，内容与源会话当前已保存的内容一致（同上，以 Known Limitations 为界）。
- 从更早的轮次 fork 时，即使最新一轮还没存好，也照样成功——晚存的是后面的轮次，与要复制的部分无关。**在一轮刚被中断、它自己还没存完时从它分叉，也照样成功**：没存完的正是被分叉掉的那一轮。
- 整份复制时，若最新一轮还没存好，明确报错并可重试，而不是悄悄产出一份缺一轮的副本。
- 源会话正在跑、有待批准的工具调用、**或还有排队等着跑的任务**时，fork 被拒绝，且没有产生任何新会话。
- AI 回复、中途调用工具的消息、工具结果、sub-agent 的消息、以及会话第一条用户消息上，都不出现 fork 入口。
- fork 入口刷新页面后仍在原处——它挂在用户消息上，而用户消息是持久化历史的一部分。
- 一次分叉在途时，该会话的所有入口（正文里可分叉的用户消息上的、以及会话列表里的）一起禁用，避免点出多份副本。
