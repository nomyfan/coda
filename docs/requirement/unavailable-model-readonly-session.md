## Problem

历史会话绑定的模型配置失效后，`open_session` 返回 `-32020: session model binding is unavailable`，连已保存的对话也无法查看。模型是否可执行不应决定用户能否读取历史；此时应以只读方式打开会话。

## Scenarios

- provider 或 model 从服务端配置移除后，用户打开原有会话，仍能查看历史消息，并看到只读原因及原模型标识。
- 模型仍存在，但会话保存的 reasoning effort 已不再受支持时，同样能以只读方式加载。
- 会话包含待审批工具调用或待回答的 `ask_user` 时，用户能查看相关内容，但不能提交决定或触发继续执行。
- 刷新页面、断线重连或服务端重启后，仍可读取这类会话；配置恢复有效后，重新打开会话可恢复原有正常行为。

## Scope

In:

- 加载并展示已有历史，包括消息、推理内容、工具调用及结果、图片和压缩记录；现有查看、展开、复制功能继续可用，已保留的后台任务结果仍可查看。
- 明确展示“模型配置不可用，当前会话只读”，保留原模型标识，避免显示成默认模型或空白会话。
- 禁止发送或继续对话、编辑重跑、审批（包括批准、拒绝、始终允许）、回答 `ask_user`、手动压缩，以及会触发执行或修改对话状态的其他操作。
- 禁止调整 reasoning effort、权限模式及分叉；分叉会继承失效的模型绑定，本次不扩展它的恢复能力。
- 保留会话列表中的重命名和删除操作（用户已确认）；沿用现有交互和约束。
- 前后端一致执行只读限制，直接调用接口也不能绕过。

Out:

- 切换模型、自动回退到默认模型、迁移历史或通过分叉更换模型。
- API 超时、限流、鉴权失败等调用阶段错误的探测、重试或自动只读处理。
- 数据库、工作区或历史数据本身不可用时的通用降级；不将其他加载失败伪装为只读成功。

## Constraints

- 以服务端当前配置能否解析会话持久化绑定为判定依据，覆盖 provider/model 缺失与 reasoning effort 不受支持。
- 保持现有会话 provider/model 固定绑定规则；只读是会话的可用状态，不是新的权限模式。
- 只读加载不触发模型请求、工具执行或自动继续，也不丢弃历史、改变模型绑定或自动处理待审批内容。

## Success Criteria

- 对缺失模型和无效 reasoning effort 分别验证：原先返回该错误的历史会话现在成功加载，并明确标为只读。
- 在只读会话中，历史内容及现有查看功能可用；重命名和删除按既有规则可用。
- 所有被禁操作在 UI 中不可用；绕过 UI 请求时服务端也不执行，不新增对话消息、不应用审批、不写入“始终允许”规则。
- 首次只读打开、刷新、重连和服务端重启后均满足上述行为，待审批内容不会因查看而被执行或丢弃。
- 配置恢复后重新打开可正常使用；配置有效的会话、新建会话及现有模型绑定规则不受影响。
