# Upstream Generation Model Requirements

## Problem

`GenerationMetadata` 当前只记录本次请求的 provider、模型和 reasoning effort。请求使用别名或上游发生模型映射、路由时，历史消息仍显示请求模型，无法看出上游报告由哪个模型生成了回复。

本需求把“实际调用模型”限定为**上游响应报告的模型标识**。它可能是具体版本，也可能仍是公开模型名；Coda 不据此声称验证了底层权重版本或执行供应商。

## Scenarios

- 请求模型为 A，上游响应 `model` 为 B：用户查看该条回复时看到 B，同时能查看当时请求的 A。
- 上游返回与请求相同的模型名：仍按上游返回值记录，不能因为两者相同就判断它只是回显或已解析为固定版本。
- 用户中断已输出正文或 reasoning 的生成：保留下来的部分回复带上中断前已接收的模型信息。
- root、继承模型的子代理、显式覆盖模型的子代理分别生成消息：每条消息记录自己的请求和响应信息。
- 用户切换会话模型、重连、重新打开、fork 或 rewind 后查看历史：保留消息仍显示生成当时记录的信息。

## Scope

纳入：

- 当前 `generic`、`deepseek`、`openrouter` 三种 OpenAI-compatible Chat Completions 适配路径中的响应 `model`。
- 保留现有请求信息，新增独立的上游模型记录；覆盖正常完成、仅工具调用的 assistant 消息，以及现有机制保存的用户中断消息。
- 随消息持久化，通过现有历史和 `llm_end` 传输，并用于现有消息模型标签。
- 缺失、空白或字段类型异常时保持生成可用；显示请求模型时明确标明来源。

不纳入：

- 实际执行供应商、完整 fallback/重试链、request ID、fingerprint、原始响应归档及计费审计；这些属于更广的调用追踪需求。
- 新增 Anthropic Messages / Responses API、主动查询模型别名、按厂商维护“已验证实际模型”映射。
- 改变模型选择、family 校验、reasoning effort、请求路由，以及为失败调用或纯 metadata 响应新增历史消息。
- 流式生成期间实时更新模型标签；本次沿用 `llm_end` 后显示消息模型的时机。

## Constraints

- 上游模型允许不在本地模型目录中；不能因此拒绝回复或改写会话绑定。
- 上游未提供的信息保持未知，不能用请求模型、当前配置或后续查询结果冒充历史响应值。
- 同一流出现不同的有效模型名时，记录最后收到的值，含义仅为“上游最后报告的模型”；本次不保存变化链。
- 元数据随消息保存，不进入发给模型的对话内容；不要求额外网络请求。

## Success Criteria

1. 请求 A、响应 B 时，持久化和 `llm_end` 同时保留 A、B，现有消息标签显示 B，详情可区分请求与响应。
2. `model` 只在首个、最后一个或 `choices: []` 的 chunk 中出现时均能记录；不依赖 usage、正文或 reasoning 是否存在。
3. 缺失、`null`、空白或非字符串 `model` 不破坏原本有效的生成，不清除先前有效值；全程没有有效值时不伪造上游模型。
4. 用户中断产生的持久化部分消息保留已接收的上游模型；尚未接收时保持未知。
5. 并行进程和相邻生成之间不会串用模型信息；重连、冷打开、fork、rewind 和切换模型不会改写保留消息的记录。
6. 原有仅含请求信息的消息仍明确按请求信息展示；没有 `generation` 的消息不从当前会话补造模型信息。
